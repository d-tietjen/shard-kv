# `shard-kv` Release Announcement

Since 2023, I've been deeply embedded in the database space, working on database wire protocols, internals, and more. Then as a startup founder working on database and infrastructure solutions for enterprise, I got a firsthand glimpse at how customers actually deploy and interact with these systems for production workloads. What I saw shocked me, with the most confusing part being the way companies deployed and managed their caching infrastructure.

A cache is a relatively simple construct, a performant and highly available data store that sits as close to the caller as possible, reducing load on primary data sources and overall latency for repeated queries. However, not all caches are created equal, and while Redis is the name-brand solution, Redis is only a server offering. There are also many language-specific embedded options for native caches that don't require networking or TCP.

As we proved in the benchmarks for `shard-kv`, handling concurrent client requests over TCP consumes the majority of CPU load: a 1 vCPU deployment can reach roughly 100K requests per second, or 1M operations per second when each request is pipelined to contain multiple operations, while an embedded deployment can reach roughly 7M requests per second. That 70x performance improvement isn't just reduced networking; it is the removal of networking from the hot path. When deployed as a server, the cache does all the same work as an embedded instance, but must also handle TCP connections, parse wire protocols, transform requests to packets, and schedule parallel operations. This added cost has a drastic negative performance impact. Despite that TCP cost, we saw organizations reach for Redis time and time again, even when running workloads on the same server. Even when it makes sense to leverage an independent caching server, colocation becomes more important. An embedded cache can deliver data in under a microsecond. Local TCP takes at least 100 microseconds. When deployed as a managed server, especially in the cloud, latency can reach 10+ milliseconds per request. While still better than some direct database queries, that's 10,000x higher latency than an embedded deployment and 70x less throughput per vCPU, or 7x less if requests are pipelined.

The devil's advocate may argue this isolation of workloads is necessary for scalability. However, Redis is limited to a single CPU thread, so the database doesn't natively benefit from vertical scaling. This was the inspiration for competitive solutions such as Dragonfly, which demonstrate the performance benefits of scaling across shards but still leave performance on the table for server deployments.

So the question we asked was: given these unreasonable economics, why not design a better embedded cache that can also be deployed as a server, optimized to maximize performance on the smallest possible footprint while scaling across vCPU threads as they are made available? This provides the best of both worlds while still allowing for Redis RESP protocol compatibility.

After a series of successful experiments in early 2026, we have officially released `shard-kv`: `shardmap` for embedded Rust workloads and `shardcache` for Redis-compatible server deployments, both optimized for high-throughput and high-volume workloads.
