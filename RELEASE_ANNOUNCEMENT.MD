# `fast-cache` Release Announcement

Since 2023, I've been deeply embedded in the database space, working on database wire-protocols, internals and more. Then as a startup founder, working on database and infrastructure solutions for enterprise I got a first hand glimpse at how customers actually deploy and interact with these systems for production workloads. What I saw shocked me, with the most confusing being the way companies deployed and managed their caching infrastructure.

A cache is a relatively simple construct, a performant and highly availabile data-store that sits as close to the caller as possible, reducing load on primary data sources and overall latency for repeated queries. However, not all caches are created equal, and while Redis is the name brand solution, Redis is only a server offering, and there are many language specific embedded options for native caches that don't require networking or TCP.

As we proved in the benchmarks for `fast-cache` handling concurrent clients requests over TCP consumes the majority of CPU load, where a 1 vCPU deployment can only ~100K req/s (or 1M ops/s when each request is popelined to contain multiple operations) while an embedded deployment can ready ~7M req/s. That 70x performance improvement isn't just reduced networking, but the simplification of networking. When deployed as a server, the cache does all the same work as an embedded instance, but must handle TCP connections, parsing wire-protocols, transforming requests to packets, and scheduling parallel operations. This added cost has a drastic negative performance impact. However, despite the expensive cost of TCP, we saw organizations reach for Redis, time and time again, even when running workloads on the same server. However, even if it makes sense to leverage an independent caching server, colocation becomes even more important. An embedded cache can deliver data in under a microsecond. Local TCP takes at least 100 microseconds. But when deployed as a server, especially in the cloud, most enterprises use PaaS solutions, where latency can reach 10+ milliseconds per request. While still better that some direct database queries, that's 10,000x increased latency when compared to an embedded deployment for 70x less performance per vCPU (7x if requests are pipelined).

The devil's advocate may argue this isolation of workloads is neccessary for scalability; however, when considering that Redis is limited to a single CPU thread, the database doesn't natively benefit from vertical scalability of resources. This was the inspiration for competitive solutions such as Dragonfly, which demonstrate the performance benefits of scaling across shards, but still leave performance on the table for server deployments.

So the question we asked was, given these unreasonable economics, why not design a better embedded cache that can also be deployed as a server, hyper-optimized to maximize performance on the smallest possible footprint while scaling acrsoss vCPU threads as they are made available. This provides the best of all worlds, while still allowing for Redis RESP protocol compatability

After a series of successful experiments in early 2026, we have officialy released `fast-cache`, a Rust native embedded first caching database hyper-optimized for high-throughput and high-volume workloads.
